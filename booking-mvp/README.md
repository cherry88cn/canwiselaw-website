# CanWise Booking MVP

Development deliverable, not a deployed booking service. Existing Calendly links, production build and `main` remain unchanged. The website remains hosted by GitHub Pages. This directory is a self-contained source module, not generated by the existing site builder.

## Contents

- `web/`: bilingual standalone website form using the existing logo, colours and self-hosted Chinese font. Preview at `/booking-mvp/web/` from the repository root. No API is configured by default; it cannot accidentally submit real requests.
- `apps-script/`: Google-hosted API and explicit OAuth manifest. Calendar access is FreeBusy only. No events are read or created.
- `relay/`: optional Cloudflare Worker for CORS, Google redirects and a stable public HTTPS endpoint. Free tier is a candidate, not a guarantee of mainland reachability.
- `miniprogram/`: Chinese native mini-program scaffold. `touristappid` is a development placeholder, not a registered mini-program. No WeChat credentials needed for code delivery.
- `docs/SETUP.zh-CN.md`: deployment, permissions, evening override and daily operation.
- `docs/API.md`: shared contract and failure semantics.
- `docs/WORKBUDDY.zh-CN.md`: copyable continuation prompt and acceptance checklist.
- `docs/VALIDATION.md`: verification status and mainland test plan.

## Confirmed behaviour

One lawyer; 60-minute consultation; CAD $350/hour shown, no payment integration. Weekdays 10:00–17:00 Toronto, at least 24 hours ahead, through the Toronto date 30 days from now. Starts every 15 minutes; consultation plus 15-minute post-buffer must fit within an open window (last regular start 15:45). Overrides add dated windows, including evenings/weekends, visible to everyone. Busy intervals still exclude conflicting slots.

All submissions are requests pending manual confirmation, not reservations. Pending requests do not block availability. No client confirmation email. The lawyer contacts the client and manages any calendar entries manually. WeChat contact does not require email. WeChat also supports unverified preferred-time text for manual discussion; it cannot reserve a time outside the scheduling rules.

## Privacy and limitations

Only Google receives the Calendar OAuth token and raw FreeBusy intervals. Website/WeChat/relay receive derived available slots, which still reveal limited availability. Relay processes client-submitted contact data in transit. No payload logging, analytics, KV storage or database is configured there. Check platform logging settings before deployment.

The API is public. CORS is not authentication. Honeypot, field limits, a 50-new-requests/day server cap and short write lock provide modest protection, not full anti-abuse or appointment concurrency guarantees. Public availability queries can exhaust Google quotas; reassess abuse controls if observed. Idempotency prevents repeat saves in the same active form; it does not deduplicate separate customers or reloads. Never place a static secret in web or mini-program code.

Sheets scope grants access to spreadsheets available to the authorizing account, not only the configured sheet. The application code limits itself to `SHEET_ID`; do not describe this as a single-sheet OAuth grant. MailApp permission sends mail; no Gmail inbox scope is requested.

No offline queue, automated retry, payment, automatic expiry/deletion, reminder, client login or calendar write-back. Review the sheet directly in case email fails. Retain requests for 90 days then manually clean up; Google version history/backups may retain prior contents. This is not a guaranteed permanent-erasure mechanism.
